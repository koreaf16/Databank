# 스키마 변경(DDL Migration) 가이드

DataBank는 별도 마이그레이션 도구(Prisma migrate, Flyway 등) 없이 코드 기반 `ensureXxxSchema` 패턴을 쓴다([ADR 0002](../architecture/adr/0002-no-orm-raw-sql.md)).

## 기본 원칙

1. **DDL은 멱등**: ORA-00955(이미 존재) 발생하면 swallow
2. **신규 컬럼 추가**: `MIGRATION_DDL` 배열에 ALTER 문을 추가하고 try/catch로 무시
3. **컬럼 제거**: 다음 릴리스에 `ALTER TABLE ... DROP COLUMN ...` 추가
4. **데이터 복구가 필요한 변환**: 별도 스크립트(`backend/src/scripts/<migration>.js`)

## 신규 테이블 추가

```javascript
const TABLES = [
  `CREATE TABLE NEW_TABLE (
     ID NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY,
     NAME VARCHAR2(200 CHAR) NOT NULL,
     ...
   )`,
];

async function ensureXxxSchema(connection) {
  for (const ddl of TABLES) {
    try { await connection.execute(ddl); }
    catch (err) { if (!isAlreadyExists(err)) throw err; }
  }
  await connection.commit();
}
```

`backend/src/scripts/initSchema.js`에 호출 추가:
```javascript
await ensureNewSchema(connection);
```

## 신규 컬럼 추가

같은 schema 파일의 `MIGRATION_DDL` 배열에 ALTER 추가:

```javascript
const MIGRATION_DDL = [
  `ALTER TABLE EXAMPLES ADD MEMO CLOB`,
  `ALTER TABLE EXAMPLES ADD DEPRECATED_AT TIMESTAMP`,
];

for (const ddl of MIGRATION_DDL) {
  try { await connection.execute(ddl); }
  catch (err) { /* 이미 존재 또는 오류 — swallow */ }
}
```

ORA-01430(이미 존재) 외 다른 오류도 swallow되므로 SQL Plus나 dev DB에서 미리 검증할 것.

## 컬럼 제거

1. 한 릴리스: 컬럼을 코드에서 더 이상 사용하지 않게 변경
2. 다음 릴리스: `MIGRATION_DDL`에 `ALTER TABLE EXAMPLES DROP COLUMN OLD_COL` 추가
3. 그 다음 릴리스: 이 ALTER도 제거

## 인덱스 추가

```javascript
const MIGRATION_DDL = [
  `CREATE INDEX IDX_EXAMPLES_NAME ON EXAMPLES(NAME)`,
];
```

ORA-00955 swallow.

## 외래키 추가/제거

추가는 일반적으로 안전. 제거는 운영 영향 — 별도 ADR 작성.

## 데이터 변환 (백필)

스키마 변경에 따라 기존 데이터 변환이 필요하면 별도 스크립트:

```javascript
// backend/src/scripts/2026_05_backfill_status.js
async function run() {
  await withTransaction(async (connection) => {
    await connection.execute(`UPDATE EXAMPLES SET STATUS = 'active' WHERE STATUS IS NULL`);
  });
}
run().then(() => process.exit(0)).catch(err => { console.error(err); process.exit(1); });
```

CI/배포 파이프라인에 명시적으로 호출.

## 운영 환경 적용 절차

1. dev/staging에서 검증 — 새 ensureXxxSchema 호출 후 정상 기동 확인
2. 운영: 점검 시간대 또는 안전한 시각에 백엔드 재시작 → ensureXxxSchema 자동 실행
3. 적용 후 `SELECT * FROM USER_TAB_COLUMNS WHERE TABLE_NAME='...'` 등으로 확인

## 흔한 함정

| 증상 | 원인 / 대응 |
|---|---|
| ALTER가 적용 안 됨 | 같은 백엔드 인스턴스가 이미 떠 있음 — 재기동 필요 |
| ORA-02329 (EXP/IMP) | 일부 환경에서 IDENTITY 동작 차이 — 19c 권장 |
| 한글 잘림 | `VARCHAR2(N)`이 BYTE 단위. `VARCHAR2(N CHAR)`로 변경 |
| FK 위반 | 기존 데이터에 부모 없음 — 백필 스크립트 먼저 |
